## M14 — GC/Concurrency Hardening

Progress log for ralph/gc-concurrency-hardening branch.

## Codebase Patterns
- RuntimeTask gc_root/gc_root2 must always be initialized (JACL_NIL if unused) — test code that creates RuntimeTask manually must set both fields
- GC root scanning has three paths: currently_executing, deque snapshot, and inbox — all three must be updated in sync
- Tests that create RuntimeTask manually must be updated when the struct changes
- Use `rt_test__init_no_threads` / `rt_test__destroy_no_threads` for unit tests that don't need real worker threads
- `rt_test__ms_contains` destructively drains the mark stack but restores entries — safe for multiple checks on same stack
- `test__compile` + `rt_run_to_completion` does NOT register user procs in worker VMs — parallel body closures that call user procs will hang. Use `.jacl` tests with `# mode: concurrent` for tests that need proc calls in parallel bodies (the harness copies env to workers)
- GreyBuffer.count uses release/acquire ordering: release-store in grey_buf_push (after writing entry), acquire-load in gc__drain_grey_bufs. Use ATOMIC_STORE_EXPLICIT/ATOMIC_LOAD_EXPLICIT from platform.h — they work on non-atomic types
- Worker inbox drain: lockless volatile read of inbox_count first, then batched drain under single mutex acquisition — overflow tasks go to worker's private_deque via rt_deque_deque_push
- JaclFuture uses a CAS spinlock (volatile uint32_t), not a platform mutex — no MUTEX_DESTROY needed on GC. future_lock/future_unlock in gc.c
- CPS parallel/race bodies must use parallel_k/race_k closures (OP_COMPLETE_PARALLEL/OP_COMPLETE_RACE), NOT resolve_k + internal future — the internal-future-poll pattern breaks when bodies suspend at inner awaits
- Race tests with `# mode: concurrent` must use identical return values in both bodies for determinism (see race_concurrent.jacl pattern)
- Adding new opcodes to bytecode.c requires updating the hardcoded opcode index assertions in test/test_bytecode.c

- `grey_buf_push` (gc.c:619): reads count into local, writes entry first (plain store, thread-local), then release-stores count+1 via ATOMIC_STORE_EXPLICIT
- `gc__drain_grey_bufs` (runtime.c:597): acquire-loads count via ATOMIC_LOAD_EXPLICIT, ensuring all entries[0..count-1] are visible

- Files changed: src/gc.c, src/runtime.c
- **Learnings for future iterations:**
  - GreyBuffer is per-worker (thread-local writes) but GC thread reads count cross-thread — classic release/acquire pattern
  - The ATOMIC macros in platform.h work on non-atomic types by casting (C11 path) or using __atomic builtins (GCC path)
  - Grey buffer reset after gc_active=0 is safe as plain store: gc_active=0 (release) ensures workers stop pushing, gc_running=0 (release) publishes reset before next cycle
  - On x86/TSO, the plain stores were already safe in practice, but C11 formally requires atomic operations for cross-thread access to avoid UB

- Files changed: src/gc.c
- **Learnings for future iterations:**

  - Block pool mutex in gc.c still uses platform_mutex_t (coarse-grained, different use case) — only future locks were converted

## 2026-03-03 - US-006
Thread: (local)
- Added `# mode: concurrent` to 10 .jacl test files: spawn_multi, spawn_nested, parallel_error, parallel_with_await, parallel_await_error, race_basic, race_error, async_error_spawn, async_error_propagation, async_error_parallel
- Discovered and fixed concurrency bug: CPS parallel/race bodies with inner `spawn + await` returned nil in concurrent mode
  - Root cause: `runtime__parallel_task_exec` used resolve_k + internal future, polled the future after `vm__run`. When the body suspended at an `await`, `vm__run` returned early with the future still PENDING → `JACL_NIL` stored as result
  - Fix: introduced `parallel_k` and `race_k` closures with new opcodes `OP_COMPLETE_PARALLEL` and `OP_COMPLETE_RACE` that directly complete the aggregation slot (store result, handle error, increment counter, schedule join). Works whether the body completes synchronously or suspends and resumes asynchronously
- Race tests (race_basic, race_error) adjusted for deterministic concurrent output: both bodies return the same value (matching race_concurrent.jacl pattern)
- Updated opcode index assertions in test_bytecode.c (+2 offset for new opcodes)
- All 48 test suites pass, 172/172 .jacl tests pass, zero new compiler warnings
- Files changed: src/bytecode.c, src/vm.c, src/runtime.c, test/test_bytecode.c, 10 .jacl test files
- **Learnings for future iterations:**
  - The resolve_k + internal future pattern works for spawn tasks (where the future is the final output) but NOT for parallel/race bodies (where the result must feed back into an aggregation)
  - When a CPS body suspends at an inner await, `vm__run` returns `VM_OK` but the CPS chain is not complete — the continuation (`__k`) hasn't been called yet
  - The fix is to make `__k` itself do the completion work (parallel_k/race_k), not wrap __k in resolve_k and poll the result
  - Race tests are inherently non-deterministic in concurrent mode — both bodies may complete in any order. Use identical return values for determinism
  - New opcodes require updating test_bytecode.c's hardcoded enum value assertions
