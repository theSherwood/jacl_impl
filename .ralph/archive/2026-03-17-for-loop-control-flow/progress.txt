## Codebase Patterns
- While loops are compiled inline (not closure-wrapped) — condition/body/loop-back pattern with OP_JUMP_IF_FALSE + OP_LOOP
- Break/continue use OP_JUMP forward-patching (break) and OP_LOOP backward-jump (continue) — same technique as if/else
- OP_CHECK_ERROR after each body statement pops the value if not an error — net stack effect of loop body is zero
- Loop context stack (LoopContext) tracks break jump patches per nesting level
- Both bracket syntax `[break $val]` and bare command syntax `break $val` are supported — compiler handles AST_BREAK node AND command head "break"
- For break with value: break pushes value then jumps past OP_NIL; normal exit pushes nil then jumps over break landing zone
- For-loops are compiled as inlined loops (like while) with hidden locals: __col, __len, __idx, $it/name — uses OP_SET_LOCAL to update element each iteration
- LoopContext.is_for_loop distinguishes for vs while; for-loops use forward-jump patching for continue (while uses backward OP_LOOP)
- OP_CLOSE_LOOP pops N values under the top of stack — used by break to clean up for-loop hidden locals while preserving break value
- For HOF callback form `[for $coll $callback]`, reuse OP_EACH via compiler__compile_hof_builtin
- Test pattern: compile-and-run via jacl_run(), capture stdout with PrintCapture, ASSERT_STR_EQ
- For compile-error tests: compile_source() returns CompileResult, check error_count and strstr(error_message)
- `return` keyword: AST_RETURN node, compiles to push value (or nil) + OP_RETURN — works in both bracket `[return $val]` and bare `return $val` forms
- Since for-loop bodies are inlined, `return` inside a for block naturally exits the enclosing proc via OP_RETURN (no special handling needed)
- HOF callback form uses OP_EACH (separate call frame), so `return` in callback exits only the callback proc
- Lambda shorthand `\` is specified in SYNTAX_REDESIGN.md but NOT implemented — use named `proc` + `$callback` for HOF form tests
- Proc/variable names must be ≤ 7 chars (inline string limit) — use short names in tests
- C-style for `[for {init; cond; step} { body }]` detected by `args[0]->type == AST_BLOCK && args[1]->type == AST_BLOCK` — must be checked BEFORE collection-based form detection
- C-style for uses `begin_scope`/`end_scope` for init variable scoping; `is_for_loop=true` so continue uses forward-jump patching and break uses OP_CLOSE_LOOP
- After loop, init vars become out-of-scope locals → accessing them is a **runtime** error (not compile-time), because undefined vars fall through to global lookup
- Mutable variable update command is `set!` not `set` — use `[set! varname expr]` syntax in tests

- **Learnings for future iterations:**
  - `for` syntax does not exist in the old codebase — it was planned in the syntax redesign but never merged. Had to implement it from scratch as part of this story to satisfy the acceptance criteria
  - For inlined for-loops, break needs OP_CLOSE_LOOP because break value sits ON TOP of hidden locals (__col, __len, __idx, $it). A simple OP_POP_N would pop the value too. OP_CLOSE_LOOP slides TOS down past N stack entries
  - Continue in for-loops uses forward-jump patching (like break) because the increment code is AFTER the body. While-loop continue uses backward OP_LOOP because condition is BEFORE the body
  - Pre-allocated element slot with OP_SET_LOCAL avoids creating new locals each iteration and keeps the stack layout stable
  - Adding opcodes shifts OP_HALT — test_bytecode.c has ordinal assertions that must be updated
