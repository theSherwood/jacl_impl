## Codebase Patterns
- Unity build: src/jacl.c is the unity build entrypoint; it includes value.c, gc.c, gc_collect.c, vm.c, etc. in a specific order. jacl.c does NOT include jacl.h.
- Type duplication convention: jacl.h declares public types (GCHeader, JaclSyntax, SyntaxKind, etc.) for external consumers (tests). Unity build source files (gc.c) have their own parallel definitions. The two must stay byte-identical. This is the established pattern — don't try to "deduplicate" it.
- Test builds: test/ files include src/jacl.h and link against .build/libjacl.a. lib/ tests compile standalone.
- Running tests on macOS: stdout is fully buffered when not a TTY. Use `stdbuf -o0 -e0 timeout N .build/<test>` to see output when killed.
- Pre-existing broken tests (on HEAD f8d63e3): parser, e2e_struct_tramp, embed. Not related to macro work.
- VMFormatBuf usage: init with `VMFormatBuf buf = {0}; buf.arena = &arena;` — vm__fmt_ensure handles cap==0 by seeding to 128.
- build.sh takes --test=NAME for single-test filter; --clean clears .build.
- syntax_from_ast signature: JaclVal syntax_from_ast(AstNode *node, ThreadHeap *heap, JaclInternTable *intern). Returns JACL_NIL for NULL nodes or AST_ERROR.
- build.sh now auto-detects platform changes (macOS ↔ Linux) via .build/.platform stamp. All 84 tests (lib/ + test/) should pass on a clean build.
- syntax_to_ast signature: AstNode *syntax_to_ast(JaclVal syn_val, arena_t *arena). Returns NULL for JACL_NIL or non-syntax values.
- For string round-trip: use jacl_string_byte_len() + jacl_string_data() to copy JaclVal strings into arena memory.
- Pretty-printer does NOT always re-emit quotes: "hello" parses as AST_LIT_STRING but prints as bare `hello`. Compare against ast_pretty_print of the original, not the source text.
- TokenType and AstNodeType enums are ALSO duplicated in jacl.h (like SyntaxKind). When adding a new token or AST node type, update BOTH the source .c file AND jacl.h, keeping them byte-identical.
- When adding a new keyword token: update (1) TokenType enum in lexer.c AND jacl.h, (2) keyword switch table in lexer.c, (3) keyword-as-atom case lists in parser.c (3 places: parser__parse_atom, parser__parse_cmd_operand, parser__parse_cmd_operand default switch), (4) top-level dispatch in parser_parse.
- When adding a new AST node type: update (1) AstNodeType enum in ast.c AND jacl.h, (2) AstNode union in ast.c AND jacl.h, (3) pretty-printer in ast.c, (4) syntax_from_ast and syntax_to_ast in syntax.c if convertible, (5) SyntaxKind enum in gc.c AND jacl.h if adding a syntax kind, (6) GC tracing in gc_collect.c, (7) compiler.c main switch.
- When producing a parser error for an unexpected token, always advance past the offending token first to avoid infinite loops in the top-level parse loop.
- Compiler struct also duplicated: the Compiler struct in compiler.c AND jacl.h must have identical fields. When adding a field to the Compiler struct, update both files.
- CompileResult struct also duplicated in compiler.c AND jacl.h. Same rule: keep them byte-identical.
- When forward-declaring a typedef'd struct in compiler.c, use `typedef struct Foo Foo;` before CompileResult, then `struct Foo { ... };` at the definition site.
- MacroTable is allocated in compiler_compile and stored in both Compiler.macro_table and CompileResult.macro_table.
- Special forms that are lexer keywords (if, proc, def, mut, set, while, for, match, break, continue, return, try, quote, defmacro, syntax-quote) are caught at parse time if used as defmacro name. Non-keyword special forms (spawn, yield, await, parallel, defstruct, to) are caught at compile time by macro__is_special_form.
- Inside syntax-quote, `~cond` (bare word) parses as AST_UNQUOTE(AST_LIT_STRING("cond")), not AST_VAR_REF. Template expansion must handle both SYNTAX_LIT_STRING and SYNTAX_VAR_REF children of unquotes for parameter matching.
- Expansion pass and compiler pass share the same MacroTable. The expansion pass registers entries with closure=NULL (body AST only), and the compiler pass fills in the closure. The compiler must NOT treat a closure==NULL entry as a duplicate error.
- String comparison from JaclVal: `jacl_string_data(v, buf, sizeof(buf))` returns the byte length and copies into buf (NOT a pointer accessor). Null-terminate with `buf[n] = '\0'` before ASSERT_STR_EQ. This is the pattern used everywhere in test/test_syntax.c.
- Directly invoking a compiled closure from a C test without a JaclVM wrapper: put closure at stack[0], args at stack[1..N], set stack_top, configure frames[0] with stack_base=1 and chunk=&cl->chunk, point vm->chunk/top_chunk/ip at the closure's chunk, call vm__run(vm, 0). Result lands at vm->stack[0] after OP_RETURN drops frame_count to 0. See us010_run_closure in test/test_syntax.c.
- Inside syntax-quote, `~bareword` parses as AST_UNQUOTE(AST_LIT_STRING). The compiler must synthesize an AST_VAR_REF from the lit-string before compiling (via syntax__compile_unquote_child in compiler.c) so the closure does a parameter lookup, not a string literal push.
- Jacl has no `not` or `eq` builtins — use `==` for equality, and `if cond {} else-body` (3-arg if with empty then-branch) to invert a condition. The PRD example `syntax-quote [if [not ~cond] ~body]` is aspirational; `syntax-quote [if ~cond {} ~body]` is equivalent and works today.
- `def` creates an immutable binding — `set` on a def'd variable errors with "cannot mutate immutable binding". Use `mut` for mutable globals.
- jacl_eval runs the full pipeline (lex → parse → compiler_compile → vm_exec) and compiler_compile invokes ast_expand_macros internally, so macros Just Work from embed code without any extra wiring.
- Binding handlers (mut/set/def) now accept AST_VAR_REF in three forms: (1) plain lit-string name, (2) is_caret=1 (^name, scope mark 0), (3) is_gensym=1 (gensym output, scope mark = var-ref's own). Adding a new "name-introduction" form means extending all 3 handlers (~lines 4700 for mut, ~4840 for set, ~5310 for def).
- `quote` / `syntax-quote` are prefix forms that consume their following expression via parse_expr — so `quote +` does NOT parse (operator tokens aren't primary expressions), and `[quote [expr]]` makes a command with AST_QUOTE head + 0 args (not a 1-element arg list). To quote an operator symbol, use `syntax-head quote [+ 1 2]` or `make-syntax lit-string "+"`. To put a quoted value inside a vec, write `[vec quote [...]]` (NOT `[vec [quote [...]]]`).
- OP_SYNTAX_OP subop assignments: 0=kind, 1=datum, 2=head, 3=args, 4=commands, 5=pos, 6=string, 7=make lit-int, 8=make lit-float, 9=make lit-string, 10=make var-ref, 11=make command, 12=make block. Subops 0-6 pop a single syntax operand (introspection); subops 7-12 pop kind-specific operands (construction) and are branched before the shared introspection pop in vm.c.

## 2026-04-10 - US-012 — Scope marks on syntax objects for hygiene
Thread: (inline)
- Implemented hygienic macro expansion via scope marks, so macro-introduced locals do not shadow caller-referenced identifiers passed through `~`.
- Core idea: every AstNode carries a `uint32_t scope_mark` (0 = hand-written code, >0 = macro expansion mark). A new local (or upvalue) is tagged with the compiler's current mark, and resolve_local matches on (name, mark) with a fallback to mark 0 for inside-macro references to user globals/builtins.
- src/ast.c + src/jacl.h: added `scope_mark` field to AstNode, Local, Upvalue, and Compiler structs (all four structs are duplicated across compiler.c and jacl.h — updated both copies).
- src/syntax.c: added a per-process counter `expand__scope_counter` (starts at 0, incremented for each macro expansion). New helpers `expand__stamp_syntax` / `expand__stamp_vec` walk a freshly-cloned template and stamp every node with the fresh mark. Substitution (`expand__subst_template`) propagates the mark on copied commands/blocks; unquoted argument values are returned as-is so they keep their original (caller's) marks.
- src/syntax.c: `syntax_from_ast` now **preserves** `node->scope_mark` instead of resetting to 0. This is crucial for iterative expansion — when the expander re-reads an argument that was already substituted from a previous expansion, the existing marks must survive the AST↔syntax round-trip.

- src/compiler.c: `compiler__add_local` stamps new locals with `c->current_scope_mark`; `compiler__resolve_local` does two passes: match at current mark, then (if current mark ≠ 0) fall back to mark 0. `compiler__add_upvalue` / `compiler__resolve_upvalue` propagate scope_mark through closure captures. Upvalue resolution temporarily writes the child compiler's mark into the enclosing compiler's `current_scope_mark` so that `resolve_local` on the enclosing uses the **reference site's** mark, not whatever the enclosing happens to be compiling.
- src/compiler.c: each of the 5 sub-compiler init sites (`compile_node` closure bodies, proc bodies, defmacro body compilation) copies `body_compiler.current_scope_mark = c->current_scope_mark` after `compiler__init` — so params added before `compile_node` descends into the body get the correct mark.
- test/test_syntax.c: added 3 US-012 tests:
  - `test_us012_hygiene_local_shadow`: the PRD example — `defmacro m {x} { syntax-quote { mut tmp 1; [+ ~x $tmp] } }` then inside a proc `mut tmp 99; m $tmp` returns 100 (not 2).
  - `test_us012_hygiene_nested_macros`: `add_ten` and `add_hundred` both introduce a local `t`; nested call `add_hundred $t` starting from caller's `t = 0` returns 110.
  - `test_us012_global_fallback_still_works`: regression check that macros can still reference globals/builtins like `+` — `double 21` still returns 42.
- Files changed: src/ast.c, src/syntax.c, src/compiler.c, src/jacl.h, test/test_syntax.c, .ralph/prd.json, .ralph/progress.txt
- Verification: ./build.sh → 84/84 binaries pass, 112 syntax subtests pass, no warnings with -Wall -Wextra.
- **Learnings for future iterations:**
  - Hygiene needs scope_mark to survive EVERY AST→syntax→AST round trip. Iterative expansion (where a macro expands to code containing another macro call) re-feeds previously-substituted ASTs through `syntax_from_ast`, and if that path resets the mark to 0, you lose hygiene silently — the test fails non-obviously with a "mostly right" number (e.g. 10 instead of 110).
  - When adding a `current_scope_mark` to the compiler, the temptation is to guard `if (node->scope_mark != 0) c->current_scope_mark = node->scope_mark;` — DON'T. Unquoted sub-nodes with mark 0 are nested inside mark-M templates, and they must restore mark 0 to look up the caller's bindings. Always assign unconditionally, save/restore around the call.
  - For upvalue resolution across a closure boundary, propagate the child's `current_scope_mark` into the enclosing compiler during the call, then restore. Otherwise the enclosing's own unrelated mark leaks into the lookup.
  - `jacl_inline_string` caps at 7 bytes, so you cannot mangle names by appending a mark suffix. Adding a sidecar `scope_mark` field on Local/Upvalue is the right call.
  - Sub-compilers (proc/closure body compilers) must inherit `current_scope_mark` from the parent in their init site — parameters added before `compile_node` runs on the body will otherwise be stamped with 0 and the macro-introduced references won't resolve through them.

- **Learnings for future iterations:**
  - JACL macros are template-based substitution, not runtime evaluation. This means builtins that are "supposed to be called during macro expansion" (like gensym in traditional Lisps) cannot be registered as regular native functions and called via opcodes — there is no interpreter running during `expand__subst_template`. The only path is to recognize the call *as a syntactic form* inside the template walker and synthesize its result directly. If the PRD says a feature needs to run during expansion, think "template form", not "builtin function".

With 2 bytes reserved for the `__` separator and at least 1-2 for a decimal counter, you get roughly 3 bytes for the prefix. A simple base-10 counter cap the prefix accordingly; if you needed a larger namespace you'd want a base-36 or hex counter, or use gc-allocated (non-inline) strings. For gensym, 3-byte prefix is fine because macro authors shouldn't be picking long gensym prefixes anyway — `g`, `tmp`, `it` all fit.

Grep for `bind_name_ptr` to find the three sites (currently ~lines 4700, 4840, 5310).
  - The gensym counter is a static file-scope global in syntax.c. This is fine for single-threaded use but would need to be per-heap or atomic in a multi-interpreter setup. Keep this in mind when US-018 or later introduces multi-VM isolation.
  - Semantic distinction that took a moment to clarify: `^name` (caret) forces mark 0 so the binding lives in *caller scope* — uniqueness via mark. `[gensym]` keeps the current expansion mark AND uses a unique name — uniqueness via name. Both solve "avoid accidental capture", but they solve opposite ends: caret is for *intentional* capture (anaphoric macros); gensym is for *unintentional* capture (macro-private helpers). Don't collapse them into a single flag.

Native-function registration is only for 7-byte-or-less names that take their args normally. When in doubt, grep `compiler__head_matches` to see prior art.
  - A single dispatch opcode with a subop byte is a clean way to add a *family* of related builtins without bloating the opcode table. Three rules: (1) the subop byte is a `uint8_t` read via `vm__read_byte`, so you get 256 slots per family; (2) put a comment block at the top of the case listing the subop meanings; (3) keep a parallel `static const char *names[]` array for error messages so the dispatcher can print the user-level builtin name on type errors without duplicating it in each case. This pattern would also work well for future "syntax manipulation" opcodes (US-016 `make-syntax`, US-017 etc.).
  - `vm__fmt_init` / `vm__fmt_value` / `vm__fmt_*` are the internal formatter used by `stack-trace` and error messages. They write into an arena-allocated buffer (`VMFormatBuf`) and are cheap to use from any opcode handler. Handy for any builtin that needs to stringify a value; don't reinvent it.
  - The command head for `[+ 1 2]` is a `SYNTAX_LIT_STRING` (not `SYNTAX_VAR_REF`) whose datum is the operator string `"+"`. I initially expected var-ref. Reason: the parser treats operators and bare head words as lit-strings so that operator dispatch and normal command dispatch can share the same lookup path. `syntax-datum syntax-head` on an operator call gives you the operator's spelling as a plain string, which is probably what you want for most macro introspection.

## 2026-04-11 - US-016 — make-syntax construction builtin
Thread: (inline)
- Implemented `make-syntax` as a compile-time-matched builtin in `compiler__compile_command` that dispatches on the first-arg kind name (a bare word) and emits `OP_SYNTAX_OP` with one of 6 new subops (7..12). Same single-opcode/subop-byte family pattern established by US-015 introspection. Construction kinds: `lit-int`, `lit-float`, `lit-string`, `var-ref`, `command` (head + args-vec), `block` (commands-vec).
- src/compiler.c: new `compiler__head_matches(head, "make-syntax", 11)` branch that (1) requires at least 1 arg, (2) requires the first arg to be `AST_LIT_STRING`, (3) dispatches on the kind string to select a subop and required argc, (4) compiles the remaining args and emits `OP_SYNTAX_OP` + subop. Unknown kinds and wrong arities are compile errors with clear messages listing the valid kinds.
- src/vm.c: `OP_SYNTAX_OP` dispatcher now branches on `subop >= 7` BEFORE the introspection pop, because construction ops don't expect a syntax operand on top of the stack (they take strings, numbers, syntax, or vecs). Each construction subop pops its operand(s), type-checks via `jacl_is_i32` / `jacl_is_f32` / `jacl_is_string` / `jacl_is_vector` / `jacl_is_syntax`, allocates via `gc_alloc_syntax(&vm->heap)`, fills in the kind-specific union field, and pushes. The command subop also walks the args vec to verify every element is a syntax object before assembly (same invariant `gc_alloc_syntax` callers elsewhere assume).
- Scope mark: constructed syntax objects get `scope_mark = 0` (the default from `gc_alloc_syntax`). The PRD says "Constructed syntax objects get the current expansion's scope mark" but JACL's macro expansion is template-based (see the `project_macro_eval_limitation` memory), so there is no "current expansion scope mark" accessible at runtime — there's no interpreter running during `expand__subst_template`. Runtime-constructed syntax values are only useful outside of an active expansion anyway, so 0 is the correct default. Documented as a known simplification in the PRD notes.
- test/test_syntax.c: added 10 US-016 tests via `jacl_eval` — matching the end-to-end testing strategy used throughout test_syntax.c. Covered: lit-int/lit-float/lit-string/var-ref construction (+ datum round-trip), command construction (with head datum, args length, first-arg datum chain), block construction (with commands length), unknown-kind compile error, three arity compile errors (too many, too few, zero), five type errors at runtime (lit-int with string, var-ref with int, command with non-syntax head, command with non-vec args, command with non-syntax element in args vec), and a pretty-print round-trip.
- Files changed: src/compiler.c, src/vm.c, test/test_syntax.c, .ralph/prd.json, .ralph/progress.txt
- Verification: ./build.sh → 84/84 binaries pass, 144 syntax subtests pass (up from 134), no warnings with -Wall -Wextra.
- **Learnings for future iterations:**
  - The `quote` prefix form consumes its single following expression via `parser__parse_expr` (not a special bare-word reader), so `quote +` does NOT parse — `+` is `TOKEN_OPERATOR` which is not handled as a primary expression in `parser__parse_expr`. You cannot write `[quote +]` to get a 1-arg command whose arg is the `+` symbol. Workarounds: (a) quote a full bracket form and extract with syntax-head, e.g. `[syntax-head quote [+ 1 2]]`, or (b) construct the head programmatically via `[make-syntax var-ref "foo"]` or `[make-syntax lit-string "+"]`. This is exactly the path test_us015_syntax_head already uses. Any test that wants "a syntax for an operator symbol" should use approach (a) or (b).
  - Writing `[quote [+ 1 2]]` inside another bracketed command does NOT produce a vec/arg-list element containing the quoted command. It produces a *command whose head is an AST_QUOTE* and which has zero args, because `parser__parse_command` calls `parse_expr` for the head, which sees `TOKEN_QUOTE` as a prefix form and consumes `[+ 1 2]` as the quote child. The resulting form is compiled as "call the value of the quoted expression as a function" → runtime error. To put a quoted value inside a vec, write `[vec quote [+ 1 2]]` (quote is NOT bracketed separately) — the vec head consumes its own `vec` token, then parse_expr sees TOKEN_QUOTE and reads `quote [+ 1 2]` as a single arg via the prefix form. Mental model: `quote` / `syntax-quote` are word-prefix operators in any expression position, not head-position commands.
  - When adding construction ops that don't take a syntax object on top of the stack, branch on the subop BEFORE the shared introspection pop. The existing introspection path fetches the top-of-stack as a syntax object and errors otherwise, which is wrong for constructors that pop a string/number/vec. The cleanest refactor is a simple `if (subop >= construction_base) { ... break; }` guard before the introspection code.
  - For the make-syntax command subop, type-check every element of the args vec upfront (walking it once) before allocating the syntax object. Skipping per-element checks at allocation time would let bogus values slip into the AST where later introspection or expansion would misbehave far from the origin.
  - For floats, `3.14` at the literal level is an `f32` by default (see `compiler__compile_node` AST_LIT_FLOAT path). `jacl_is_f32(v)` / `jacl_as_f32(v)` pair is the runtime check; don't reach for `f64` unless the user explicitly annotated the context.

## 2026-04-11 - US-017 — syntax-error builtin for explicit compile-time errors
Thread: (inline)
- Implemented `syntax-error` as a compile-time-matched builtin in `compiler__compile_command` that dispatches to two new OP_SYNTAX_OP subops: 13 (message only) and 14 (message + syntax object). The arity check (must be 1 or 2 args) is enforced at compile time via `compiler__builtin_arity_error`; the message must be a string (runtime type check); when a second arg is present it must be a syntax object (runtime type check).
- src/compiler.c: added a `compiler__head_matches(head, "syntax-error", 12)` branch right after the make-syntax branch (~line 6907). Compiles the message arg unconditionally; if `argc == 2` also compiles the syntax arg, then emits `OP_SYNTAX_OP` + subop 14, otherwise subop 13.
- src/vm.c: added subop 13 and 14 dispatch in the `OP_SYNTAX_OP` case. Both pop their operands, type-check them, extract the message via `jacl_string_data(msg, mbuf, sizeof(mbuf)-1)` into a 192-byte stack buffer, and call `vm__set_error`. Subop 13 formats as `syntax-error: <msg>`; subop 14 as `syntax-error at <line>:<col>: <msg>` using `syn->pos_line` and `syn->pos_col`. Both branches are inserted BEFORE the existing construction (subop 7-12) check and introspection (subop 0-6) path, so they don't interact with the shared syntax-on-top-of-stack fetch. Both return `VM_RUNTIME_ERROR` to halt the VM.
- Semantic note: The PRD framed this as "halts compilation" but JACL macros are template-based (see `project_macro_eval_limitation` memory) — there is no expansion-time interpreter. The practical equivalent is "halts the program at the point the expanded `syntax-error` call runs". A macro template like `syntax-quote [syntax-error "nope"]` substitutes into the caller's AST as a regular command; when that code is reached at runtime, the error fires with the custom message. The e2e test `test_us017_syntax_error_from_macro` validates this path.
- test/test_syntax.c: added 7 US-017 tests via `jacl_eval`:
  - `test_us017_syntax_error_message_only`: `syntax-error "must be a literal"` → error whose message contains "must be a literal".
  - `test_us017_syntax_error_with_syntax`: `syntax-error "bad shape" quote [+ 1 2]` → error whose message contains "bad shape" and a `:` (line:col). Uses the prefix `quote` form, NOT bracketed `[quote ...]` — brackets would invoke `quote` as a command and try to call the resulting syntax value.
  - `test_us017_syntax_error_zero_args`: `syntax-error` → compile error.
  - `test_us017_syntax_error_too_many_args`: `syntax-error "a" quote 1 quote 2` → compile error (the parser treats it as 3 args, which violates the 1-or-2 arity).
  - `test_us017_syntax_error_non_string_message`: `syntax-error 42` → error (runtime type check).
  - `test_us017_syntax_error_non_syntax_second`: `syntax-error "msg" 42` → error (runtime type check).
  - `test_us017_syntax_error_from_macro`: `defmacro require {} { syntax-quote [syntax-error "nope"] }; require` → error whose message contains "nope". Demonstrates the template-substitution path end-to-end.
- Files changed: src/compiler.c, src/vm.c, test/test_syntax.c, .ralph/prd.json, .ralph/progress.txt
- Verification: ./build.sh → 84/84 binaries pass, 151 syntax subtests pass (up from 144), no warnings with -Wall -Wextra.
- **Learnings for future iterations:**
  - The top-level parser treats bracketed forms `[quote [+ 1 2]]` as a command invocation — at runtime this tries to call the resulting syntax-object value, which fails with "cannot call unknown value". For tests that need a quoted expression as a command argument, use the PREFIX form `quote [+ 1 2]` (no outer brackets). `quote` is a word-prefix operator and consumes the next expression as its child. This is the same gotcha documented in US-016 learnings and keeps biting — any test that starts seeing "cannot call unknown value" should check for stray brackets around a `quote`/`syntax-quote` form.
  - When adding a new OP_SYNTAX_OP subop whose operand types are NOT a single syntax object on top of stack, insert the handler BEFORE both the construction (subop 7-12) and introspection (0-6) branches, and `return VM_RUNTIME_ERROR` from the error path directly. The pattern established in US-016 (branch early, `break` out of the switch) is the right shape — just add another `if (subop == N)` guard before the existing two.
  - `jacl_string_data(v, buf, buflen)` returns the byte count copied and null-terminates nothing (the test helper `us015__string_to_cstr` explicitly writes `buf[n] = '\0'` after). When using it for a VM error message, leave 1 byte of headroom in the buffer (`sizeof(mbuf) - 1`) and null-terminate manually — `vm__set_error` takes a `%s` format and will read until null.
  - A halting builtin like syntax-error should set the error via `vm__set_error` AND `return VM_RUNTIME_ERROR` immediately from the switch case — do NOT fall through to the shared `break` at the bottom of the OP_SYNTAX_OP case, otherwise the dispatch loop will continue executing with a popped stack but no error propagation.
