## M14 — GC/Concurrency Hardening

Progress log for ralph/gc-concurrency-hardening branch.

## Codebase Patterns
- RuntimeTask gc_root/gc_root2 must always be initialized (JACL_NIL if unused) — test code that creates RuntimeTask manually must set both fields
- GC root scanning has three paths: currently_executing, deque snapshot, and inbox — all three must be updated in sync
- Tests that create RuntimeTask manually must be updated when the struct changes
- Use `rt_test__init_no_threads` / `rt_test__destroy_no_threads` for unit tests that don't need real worker threads
- `rt_test__ms_contains` destructively drains the mark stack but restores entries — safe for multiple checks on same stack
- `test__compile` + `rt_run_to_completion` does NOT register user procs in worker VMs — parallel body closures that call user procs will hang. Use `.jacl` tests with `# mode: concurrent` for tests that need proc calls in parallel bodies (the harness copies env to workers)
- GreyBuffer.count uses release/acquire ordering: release-store in grey_buf_push (after writing entry), acquire-load in gc__drain_grey_bufs. Use ATOMIC_STORE_EXPLICIT/ATOMIC_LOAD_EXPLICIT from platform.h — they work on non-atomic types
- Worker inbox drain: lockless volatile read of inbox_count first, then batched drain under single mutex acquisition — overflow tasks go to worker's private_deque via rt_deque_deque_push
- JaclFuture uses a CAS spinlock (volatile uint32_t), not a platform mutex — no MUTEX_DESTROY needed on GC. future_lock/future_unlock in gc.c

## 2026-03-03 - US-003
Thread: (local)
- Added release/acquire memory ordering to GreyBuffer.count for cross-thread consistency
- `grey_buf_push` (gc.c:619): reads count into local, writes entry first (plain store, thread-local), then release-stores count+1 via ATOMIC_STORE_EXPLICIT
- `gc__drain_grey_bufs` (runtime.c:597): acquire-loads count via ATOMIC_LOAD_EXPLICIT, ensuring all entries[0..count-1] are visible
- `gc_concurrent_collect` (runtime.c:681): grey_buf.count=0 reset kept as plain store with comment documenting ordering guarantee from gc_active=0 (release) → gc_running=0 (release) chain
- Added documenting comments in both grey_buf_push and gc__drain_grey_bufs explaining the release/acquire pairing
- Files changed: src/gc.c, src/runtime.c
- **Learnings for future iterations:**
  - GreyBuffer is per-worker (thread-local writes) but GC thread reads count cross-thread — classic release/acquire pattern
  - The ATOMIC macros in platform.h work on non-atomic types by casting (C11 path) or using __atomic builtins (GCC path)
  - Grey buffer reset after gc_active=0 is safe as plain store: gc_active=0 (release) ensures workers stop pushing, gc_running=0 (release) publishes reset before next cycle
  - On x86/TSO, the plain stores were already safe in practice, but C11 formally requires atomic operations for cross-thread access to avoid UB

- Worker loop now checks `rt->inbox_count > 0` (volatile read, no lock) before acquiring inbox_mutex
- When non-empty, single lock acquisition drains ALL pending tasks: first goes to task_val, rest pushed to worker's private_deque via rt_deque_deque_push

- ~10 line change in runtime__worker_loop (src/runtime.c lines 189-202)
- All 48 test suites pass, 172/172 .jacl tests pass, zero compiler warnings
- Files changed: src/runtime.c
- **Learnings for future iterations:**
  - inbox_count is volatile intptr_t — safe for lockless reads without atomics on all platforms
  - Overflow tasks from batched drain go to private_deque, which is checked at step 2 of the worker loop — natural load balancing
  - The inbox is a LIFO stack (pop from end), so batched drain reverses submission order for overflow tasks — acceptable since task ordering is non-deterministic in concurrent mode
  - This is a pure optimization with no behavioral change — all existing tests pass without modification

  - `jacl_future_error` (error path)
  - `jacl_future_add_waiter` (waiter registration)
- No MUTEX_DESTROY needed — spinlock is just memory, no OS resource to finalize
- 20 lines added, 8 removed in src/gc.c — all 48 test suites pass, 172/172 .jacl tests pass, zero warnings
- Files changed: src/gc.c
- **Learnings for future iterations:**
  - Future lock hold time is ~10 instructions — spinning is appropriate, no need for yield/sleep backoff
  - ATOMIC_CAS takes a pointer to expected (not a value) — reset expected=0 on each retry iteration
  - The spinlock eliminates platform_mutex_t from JaclFuture, removing the need for MUTEX_DESTROY on GC collection — on Windows this avoids leaking CRITICAL_SECTION resources
  - Block pool mutex in gc.c still uses platform_mutex_t (coarse-grained, different use case) — only future locks were converted
