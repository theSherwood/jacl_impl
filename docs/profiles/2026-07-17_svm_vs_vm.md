# SVM backend vs. old bytecode VM — perf comparison (2026-07-17)

> Base commit `c61b308`. Purpose: while the SVM migration is paused waiting on the
> upstream `exec` capability (`docs/SVM_EXEC_ASK.md`), check whether the new backend
> introduced a **performance regression** against the old bytecode VM. It did not —
> on execution the SVM JIT is **1.7×–3.4× faster** than the old VM.

## The two backends

| | old backend | new backend |
|---|---|---|
| code | `src/` bytecode compiler + tree-walking/`vm.c` dispatch VM | `runtime/` C runtime → `clang -O2` → svm-llvm → SVM IR |
| execution | bytecode interpreter loop | Cranelift **JIT** (production path) or SVM tree-walk interp |
| driver | `test/test_perf.c` (in-process, compile-once/run-N) | `runtime/harness/src/bin/bench_svm.rs` |

## Method

The hard part is comparing fairly: the old VM's bench harness times *execution only*
(compile once, submit to a runtime N times), whereas the SVM `run_with_caps(Jit)` path
**recompiles the whole linked module (~231 ms of Cranelift) on every call**, and the
one-time svm-llvm runtime translation is ~6 s. To make the numbers comparable:

1. **Same programs, both backends.** New timers run the *identical* `.jacl` files:
   - `test/bench_vm_one.c` — standalone old-VM timer over the public embed API
     (`jacl_vm_new_ex` / `jacl_eval_file`), fresh VM per iteration, min/median over N.
     Validated against `test_perf.c`: `fib(25)` min 12.59 ms here vs 12.63 ms in the
     canonical harness.
   - `runtime/harness/src/bin/bench_svm.rs` — SVM timer. Hoists the one-time runtime
     translation + codegen-driver build out of the timed region; times
     `run_with_caps(Jit)` per iteration.
2. **Isolate SVM execution.** Each SVM JIT run = *whole-module compile* + *guest
   execution*. A near-empty `_baseline` program (`print 0`) that links the same runtime
   measures the compile+startup tax alone (**231 ms**, stable to ±2 ms across runs);
   `SVM exec = jit_min − baseline_min`. The subtraction is valid because the JIT compiles
   the whole module eagerly, so the tax is scenario-independent (confirmed: baseline and
   per-scenario exec estimates reproduce within ~2% across independent runs).
3. **Scaled workloads.** Scenarios (`test/jacl/bench_scaled/`) are sized so execution is
   ~100 ms–1 s, dwarfing measurement noise and making the baseline subtraction precise.
   Every scenario's printed output is **identical** on both backends (correctness gate).

## Results — execution time (lower is better)

VM median vs. SVM-JIT isolated execution, on identical scaled programs:

| scenario | workload | VM median | SVM-JIT exec | **VM ÷ SVM** |
|---|---|---:|---:|:---:|
| `fib`              | `fib(34)`, ~18.5 M calls        | 984.9 ms | 289.1 ms | **3.41×** |
| `sieve`            | primes < 60 000                 | 769.5 ms | 318.3 ms | **2.42×** |
| `map_lookup`       | 3 M HAMT lookups                | 462.6 ms | 267.0 ms | **1.73×** |
| `box_churn`        | 3 M short-lived boxes           | 277.3 ms | 137.7 ms | **2.01×** |
| `string_concat`    | 400 ropes × 400 concats         | 119.0 ms |  58.6 ms | **2.03×** |
| `collection_churn` | 300 × (400-elt HAMT+RRB churn)  | *crashes* | 212.2 ms |   —   |

**No regression. The SVM JIT executes 1.7×–3.4× faster than the old bytecode VM** —
expected, since it emits native code through Cranelift instead of interpreting bytecode.
The lead is largest on call-heavy integer code (`fib`) and smallest on the pointer-chasing
HAMT read path (`map_lookup`), where both backends are memory-bound.

### The one caveat: per-invocation compile cost

The SVM JIT pays a **~231 ms whole-module compile on every fresh run** (`SVM raw/run` =
exec + tax, e.g. `fib` 520 ms total). This is a *cold-start* cost, not a steady-state one:
a long-lived embedding compiles once and reuses the module (`svm_run::JitSession`,
compile-once/run-many), and the one-time svm-llvm runtime translation (~6 s) is also
amortized. For the "did execution get slower" question it is correctly excluded; for
"how fast is a one-shot `jacl_svm run` cold" it dominates and is worth tracking separately
if cold-start latency becomes a goal.

## Incidental findings

1. **Old VM crashes under sustained persistent-collection churn.** Building and discarding
   ~400-element HAMT/RRB structures repeatedly (`collection_churn`, ~a dozen rounds) or a
   rope past ~500–1000 deep (`string_concat` at high scale) **segfaults the old VM**
   (recursive GC-mark / rope traversal over the C stack), even with a 512 MB heap. Note
   the shipped `test/jacl/bench/collection_churn.jacl` is already pinned at `n=200` and its
   own comment describes a "1000-entry map" it no longer builds — consistent with this
   limit having been hit before. The SVM backend runs the full churn (300 rounds) cleanly.
   This is a VM robustness bug, not a perf issue, but it is why `collection_churn` has no
   VM column above.
2. **SVM codegen rejects `incr` and C-style `for {init; cond; step}`.** The stock
   `box_churn.jacl` uses both; the SVM emit driver fails with
   `unsupported command head 'incr'`. The scaled scenarios use the `while`+`mut` form.
   (Tracked breadth gap, not a perf matter.)

## Scope / what was NOT measured

- **Concurrency scenarios** (`spawn_chain`, `parallel_map_reduce`, `atom_*`) are **not**
  compared here. They exercise the scheduler/fibers, whose SVM parity is a separate
  in-progress workstream, and the migration itself is incomplete pending the upstream
  `exec` capability. This report is scoped to single-threaded execution.
- SVM **tree-walk interpreter** times are omitted (the JIT is the production path); the
  harness can emit them with `BENCH_NO_INTERP` unset.

## Reproduce

```sh
# old VM
./build.sh --release
clang -O2 -I include test/bench_vm_one.c .build-release/libjacl.a -o .build-release/bench_vm_one -lpthread -lm -lffi
BENCH_ITERS=15 .build-release/bench_vm_one test/jacl/bench_scaled/*.jacl   # omit collection_churn — it segfaults the VM

# SVM (needs llvm-18-dev for svm-llvm)
cd runtime/harness && cargo build --release --bin bench_svm
BENCH_NO_INTERP=1 BENCH_ITERS=8 target/release/bench_svm \
    ../../test/jacl/bench_scaled/_baseline.jacl ../../test/jacl/bench_scaled/*.jacl   # _baseline (print 0) first, for the compile-tax subtraction
```

Raw data: `docs/profiles/2026-07-17_{vm,svm}_scaled.jsonl` (this run),
`docs/profiles/2026-07-17_vm_unscaled.jsonl` (old-VM `test_perf` medians, 200 iters, all 12
stock scenarios, for reference).
